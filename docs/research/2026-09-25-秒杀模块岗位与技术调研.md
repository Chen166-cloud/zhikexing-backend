# 热门课程免费试听秒杀：岗位与技术证据调研

调研日期：2026-09-25。目标：为“Redis Lua + RocketMQ 事务消息 + Agent”模块确定有招聘价值、能够证明正确性的研发范围。本文是方案依据，没有实现或运行模块。

## 1. 结论与证据边界

这个模块适合同时展示通用后端和 Agent 工程能力，前提是做成完整的“有限名额报名与权益发放”业务：并发准入、数据库约束、幂等、异步状态、失败恢复、可观测性，以及受用户身份约束的 Agent 工具调用。岗位证据支持这些能力；没有证据表明三家公司统一使用本文选定的组合，也没有证据表明校招必须做秒杀。

本文列出 **12 组主要来源：4 个岗位、6 组官方技术文档/大厂技术文章、2 个原始开源仓库**。其中 2 个岗位是本项目在 **2026-09-17 已完整核验的 2027 秋招 JD**，本次重访详情抓取受限；另有 1 个明确要求经验的腾讯社招 JD，以及 1 个未标届次的腾讯常规全职岗位。后两者仅用于理解工程深度，不计入 2027 秋招样本。

取证分级：A1-S 为此前完整核验的官方校招快照；A2-I 为本次官方域名搜索索引中的完整 JD；T 为官方技术资料；O 为原始开源仓库。索引抓取时间不等于职位发布时间，网页可访问也不证明当前仍有 HC。历史技术文章只用于稳定的工程方法，不据此宣称是 2026 年最新组件栈。

## 3. 技术文档与开源证据

### S5 Apache RocketMQ：事务消息

- [官方 Transaction Message](https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/)，T，2026-09-25 打开正文。
- 官方机制：先发送半消息，再执行生产者本地事务并提交/回滚消息；缺少明确结果时 Broker 回查。它提供最终一致性，**不保证消费结果与上游事务天然一致**，也存在事务超时回滚边界。
- **模块建议**：本地事务以持久化业务结果为依据，回查查询同一事务提交的事务记录；正常处理中返回 UNKNOWN。禁止用 Redis 剩余名额或“消息发送成功”判断数据库事务已成功。还需独立设计消费者幂等及预占对账。

### S6 Apache RocketMQ：消费重试

- [官方 Consumption Retry](https://rocketmq.apache.org/docs/featureBehavior/10consumerretrypolicy/)，T，2026-09-25 打开正文。
- 官方机制：消费失败或超时触发重试，超过上限进入死信队列；PushConsumer 和 SimpleConsumer 的配置、可见性行为不同。文档明确不应把消费失败重试当日常限速机制。
- **模块建议**：权益发放采用业务唯一约束和消费幂等；数据库提交成功后再 ACK。重试、死信积压与恢复必须可观测；死信修复后仍走同一幂等入口。限流与积压控制在准入及消费并发层实现。

### S7 Redis：Lua 脚本

- [官方 Scripting with Lua](https://redis.io/docs/latest/develop/programmability/eval-intro/)，T，2026-09-25 打开正文。
- 官方边界：Lua 在 Redis 内原子执行，执行期间阻塞其他服务活动；访问的键必须显式传入。脚本缓存可在重启/故障切换后丢失，客户端需要处理 NOSCRIPT。
- **模块建议**：用短小、有界脚本完成活动窗口、重复请求、名额预占的条件操作；键、参数和返回码固定。准备脚本重载验证；拒绝任意 Lua/SQL 工具暴露给模型。原子执行范围不能延伸成 Redis、MySQL、MQ 的全局事务。

### S8 Redis：Cluster 规范

- [官方 Redis Cluster specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)，T，2026-09-25 打开正文。
- 官方边界：多键操作要求同 slot，可用 hash tag；集群采用异步复制，故障窗口可能丢失已确认写入。一个活动的同 slot 多键操作仍可能形成热点。
- **模块建议**：键名采用一致活动标签，例如 `trial:{campaignId}:stock`；活动预占、去重键同时考虑 slot。MySQL 保留名额及报名约束作为业务事实来源；Redis 切换后必须能暂停准入、校验并重建，而不能只相信缓存计数。是否分桶由实测决定。

### S9 MCP：当前授权规范

- [官方 Authorization，2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)，T。本次访问 latest 后重定向到该版，2026-09-25 已打开正文；不把旧版 2025-06-18 当当前版本。
- 规范涉及 HTTP 传输授权、token audience 校验、每次 HTTP 请求携带授权、资源 scope，以及授权升级重试上限；不允许资源服务接受/透传不适用于自身资源的 token。STDIO 的凭据处理不照搬此 HTTP 流程。
- **模块建议**：工具适配层把受信身份映射为业务主体和 `trial:claim` 等能力；实际服务仍检查活动、资格、幂等和限流。MCP 接通本身不等于业务权限完整；认证、用户同意和业务授权是不同检查点。

### S10 美团技术团队：全链路压测平台 Quake 实践

- [2018-09-27 原文](https://tech.meituan.com/2018/09/27/quake-introduction.html)，T，2026-09-25 打开正文。**这是历史工程方法案例，不是最新框架推荐。**
- 文章强调按真实业务构造流量、覆盖基础服务、容量评估、过程监控、过载保护及故障演练，不能由一个接口压测推算整条链路能力。
- **模块建议**：同时压测课程查询、报名和结果查询，分别记录准入速度与最终发放速度；包括正常成功、售罄拒绝、重复请求、消息积压及依赖故障。个人环境使用隔离测试数据和可停止的负载，记录机器、连接池与软件配置。

### S11 Apache 原始仓库：RocketMQ 5.x Java 事务示例

- [apache/rocketmq-clients](https://github.com/apache/rocketmq-clients)及[ProducerTransactionMessageExample.java](https://github.com/apache/rocketmq-clients/blob/master/java/client/src/main/java/org/apache/rocketmq/client/java/example/ProducerTransactionMessageExample.java)，O，2026-09-25 已读仓库和源文件；同时通过公开 GitHub API 确认文件内容，blob 为 `427aabf8969b7c679cd04cc3f327e1ebd6b95c98`。
- 仓库是基于 gRPC 的 RocketMQ 5.x SDK；示例展示事务创建、发送、提交和 checker 接口。示例 checker 直接返回 COMMIT，是需由业务替换的占位逻辑。
- **模块建议**：据选定客户端版本实现可靠回查，锁定 SDK/Broker/部署兼容组合。不要混贴 4.x `TransactionMQProducer` 与 5.x API；不直接复制示例中的无条件提交作为实际事务判断。

## 4. 从证据推导的研发范围

下列是结合本项目目标的研发建议，不是招聘原文，也不是对某家公司内部架构的复刻。

### 4.1 主业务必须有明确事实与状态

业务对象应是“某场热门课程的有限免费试听资格”，不引入无必要的支付、退款或金融订单。明确活动窗口、总名额、每用户限制、资格有效期和重复请求语义。接口分开表达“受理/处理中”和“权益已发放”，模型不能把前者描述成后者。

建议以关系数据库保存权威业务状态：条件扣减要求剩余名额大于零；活动与用户的唯一约束阻止重复领取，请求唯一约束处理重试；业务变更与生产者事务结果在同一个本地事务中提交。消费者负责异步权益发放时，发放记录与事件处理记录也应原子提交。具体表名可调整，但不能让 Redis 预占成功成为最终成功的唯一证明。[依据 S5、S6、S8；该表结构为设计推导。]

### 4.2 明确三种一致性边界

| 边界 | 能依赖什么 | 必须补充什么 |
|---|---|---|
| Redis 内部预占 | 有界 Lua 条件操作 | 同 slot、重复请求语义、脚本错误处理、预占生命周期 |
| 生产者本地事务 → 消息可投递 | RocketMQ 半消息、提交和回查 | 持久事务记录、明确终态、超时策略、回查告警 |
| 消息 → 权益业务结果 | 重试与应用自己的事务 | 幂等消费、唯一约束、死信修复、结果查询 |

**Redis 预占与发送半消息之间崩溃的空隙不由 RocketMQ 自动覆盖。** 需要可追踪的预占身份、明确过期规则、对账与受状态约束的补偿。补偿不能简单定时加一：必须防止重复释放、提交与补偿并发，以及旧任务回写新活动。没有查到数据库记录，也不必然证明正在执行的原事务已经失败；回查/恢复协议要区分未开始、处理中、明确回滚与已提交，并给终态决策加并发约束。

Redis 切换可能丢预占，但数据库约束仍要阻止真实超发。重建名额时不能把一个旧快照直接覆盖正在变化的缓存；需要暂停或按版本隔离准入，再校验重建。展示“故障后的可解释拒绝、可恢复处理和库存核对”比宣称无条件 exactly-once 更可信。[依据 S5—S8。]

### 4.3 Agent 联动做在业务决策与结果解释上

建议提供受限工具：活动检索、课程匹配、报名、报名状态查询。Agent 可以根据学习目标选择课程、解释时间冲突和活动规则，在用户明确要求领取时调用报名工具，再根据真实状态说明结果。后端从受信认证上下文获取用户身份，不接受模型随意提供目标用户；读取工具和写入工具使用不同权限。

一次领取意图对应稳定请求标识；Agent 超时、中断、恢复或重新规划后先查询同一请求，不用新标识盲目再抢。确定性报名逻辑不能由 LLM 判断库存或提交事务；模型服务不可用时，普通页面报名仍可工作。保留工具 schema、权限拒绝与业务错误、请求身份和 trace 关联，避免记录原始访问令牌。[依据 S2、S4、S9；工具与交互方案为设计推导。]

### 4.4 必须交付的验证证据

| 验证场景 | 应证明的结果 |
|---|---|
| 少量名额、大量不同用户，页面与 Agent 同时请求 | 最终发放不超过总名额；单用户不重复；受理与完成统计分开 |
| 相同请求重试、同用户不同请求并发 | 返回可解释的原结果/重复状态，不重复扣减或发放 |
| Redis 预占后、半消息后、DB 提交后、Broker 提交前进程终止 | 每个中间状态可查；预占、事务结果及消息最终按协议收敛 |
| 消费 DB 提交后 ACK 前退出 | 重投不重复发放；幂等不是仅靠进程内集合 |
| Redis 切换、重复补偿、旧恢复任务晚到 | 真实报名不超发；重建及补偿可审计，不破坏已提交结果 |
| 消费积压、死信、下游暂时不可用 | 有界退避、可控恢复、告警可定位；不能吞异常假装成功 |
| Agent 越权参数、重复调用、工具超时、模型不可用 | 服务端拒绝越权；恢复关联原请求；普通报名入口可用 |

性能报告至少给出机器配置、数据规模、并发/到达率、持续时间、成功/拒绝/处理中比例、p95/p99、数据库锁等待、Lua 耗时、消息积压和完成延迟。故障报告记录恢复耗时及库存/权益对账结果。Agent 评测另统计真实任务完成率、误报成功率、工具调用正确率和授权拒绝率。只报告实测数值，不把教学仓库或公司文章中的 QPS 作为本项目成绩。
