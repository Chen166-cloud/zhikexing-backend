# 中间件与基础设施清单

整理日期：2026-09-18。依据：[改造研发方案第 4、6、11、17 节](D:/java/SpringAI/intelligent-integrated-interaction-platform/docs/upgrade-plan/2027-AI-Agent-改造研发方案.md)。

本清单描述目标架构，不表示这些组件已经接入。按组件类型去重统计，不按容器、进程或集群节点计数；pgvector 计入 PostgreSQL。

模型服务目标已确定为阿里云百炼：日常 Agent 用 `qwen3.7-flash`，Embedding 保持 `text-embedding-v4`（现有 1024 维），共用一把百炼模型 API Key。详见[模型服务与 API 配置](./模型服务与API配置.md)；此次仅保存文档决策，程序配置尚未切换。

## 1. 数量与引入范围

| 范围 | 类型数 | 组件 |
|---|---:|---|
| 核心数据与异步处理 | 5 | MySQL、PostgreSQL + pgvector、Redis、RabbitMQ、OSS |
| 观测与监控配套 | 4 | Langfuse、ClickHouse、Prometheus、Grafana |
| 部署配套，另列 | — | 反向代理（原方案未选定产品）、按需独立部署的 OpenTelemetry Collector |
| 按需求扩展 | 4 | Elasticsearch、LiteLLM Proxy、vLLM、Temporal |

明确命名的“核心 + 自托管观测”共 9 类，并非第一天必须全部安装。原方案只指定反向代理职责，未锁定具体产品，不把 Nginx 等实现当成已确定选型。OpenTelemetry 原本也包含应用 SDK，只有后续选择独立部署 Collector 时才额外计入一个服务组件。

最小开发闭环先用 MySQL、PostgreSQL + pgvector、Redis、OSS，共 4 类；可靠投递阶段加入 RabbitMQ。观测组件逐步接入，若使用托管 Langfuse，则不需要自己部署其 ClickHouse 等服务。应用后端、前端、外部模型 API 未算入中间件数量。

## 2. 核心组件：5 类

| 组件 | 类型与当前基础 | 在本项目中的具体职责 | 关键边界 |
|---|---|---|---|
| **MySQL** | 业务关系数据库；现有项目已有 | 用户、空间成员、权限、课程、校区、预约；会话归属元数据；审批、工具执行结果、幂等记录；提交请求和业务 outbox | Java 服务负责业务写入；通过事务、唯一约束和条件更新保证业务一致性。完整消息/Agent 运行状态由 PG 管理 |
| **PostgreSQL + pgvector** | Agent/知识关系数据库 + 向量扩展；新增 | Agent run、attempt、租约、事件、checkpoint、完整消息、长期记忆；文档版本、chunk、向量；入库任务、inbox、评测数据与结果 | Python 服务负责；pgvector 为同一数据库内的扩展，不另算一个数据库。checkpoint 不能独自保证外部写操作幂等 |
| **Redis** | 缓存/会话/限流；现有项目已有 | 延续 Redis 登录态；热点课程/只读工具短缓存；用户与空间限流、临时通知 | 新知识向量逐步迁到 pgvector；Redis 向量链路保留作旧版 baseline。审批和最终任务状态不只放在 Redis |
| **RabbitMQ** | 消息中间件；新增、可靠性阶段引入 | Java 向 Python 投递 Agent/文档任务；审批决定和补充输入唤醒任务；重试、死信与削峰 | 结合 outbox/inbox 和幂等消费。消费者先保存持久化作业再 ACK；逐 Token 流走 SSE，不塞进 MQ |
| **阿里云 OSS** | 对象存储；现有项目已有 | PDF 原文、解析产物、附件、评测报告及其他大文件 | 数据库保存对象引用、hash、版本与权限。对象下载经授权；大文件不塞进消息体或 checkpoint |

MySQL 与 PostgreSQL 的分工是本方案的工程选择，不是技术上的强制条件。保留 MySQL 可以沿用当前 Java 业务；PostgreSQL 同时承担 Agent 持久化和向量数据。若后续决定降低运维成本，可把业务也迁入 PostgreSQL，但仍保留不同服务的数据所有权与权限隔离。

## 3. 观测与监控：4 类配套

| 组件 | 在项目中承担的功能 | 何时引入 / 注意事项 |
|---|---|---|
| **Langfuse** | 展示模型调用与 Agent 轨迹，关联 prompt/model 版本、Token、延迟、费用和评测；从失败样本跳转到对应运行 | 评测/观测阶段推荐；支持托管或自托管 |
| **ClickHouse** | 存储和分析自托管 Langfuse 的高体量观测数据，如调用事件、trace/observation 数据 | 作为 Langfuse 自托管配套，不作为课程/预约业务库 |
| **Prometheus** | 采集和保存运行指标：API 延迟/错误率、JVM、数据库连接池、worker/队列积压、活跃任务、模型限流等 | 完整运行监控阶段；告警通知路由若有需求再补专门组件 |
| **Grafana** | 将 Prometheus 等数据源中的指标做成运行看板，观察资源、吞吐、p95、错误和队列趋势 | 与指标体系配套；它主要展示数据，不替代 Prometheus 的指标存储 |

两类观测的主要用途：Langfuse 帮助分析某个 Agent 任务的模型、工具与效果；Prometheus/Grafana 帮助判断整个系统的服务和资源是否健康；OpenTelemetry 帮助关联跨服务调用。

自托管 Langfuse 还使用 PostgreSQL、Redis、对象存储等依赖。这些类型已在核心表出现，不重复计数。开发环境可以在兼容前提下共享部分实例，但要隔离数据库/用户、key 空间与 bucket；上线是否拆实例取决于容量、故障隔离和部署要求。

现有 OSS 是否能直接满足所选 Langfuse 版本的 S3-compatible 接口要求，需单独验证；不能因为“都是对象存储”就默认可以复用。必要时为观测系统配独立兼容存储，届时更新部署清单。

Langfuse 的 web/worker 和多副本也会增加容器数，所以“9 类组件”不是“9 个容器”。原方案引用的依据：[Langfuse 自托管部署](https://langfuse.com/self-hosting/deployment/docker-compose)、[Langfuse 架构](https://langfuse.com/handbook/product-engineering/architecture)。

## 4. 部署配套：反向代理与可选 Collector

**反向代理，原方案暂未锁定具体产品。** 托管 Vue 静态资源，提供统一域名与 HTTPS 入口，将 /api 转发到 Java BFF，并正确转发 SSE 长连接。

对本项目尤其要配置 SSE 路径的缓冲和超时，否则后端逐步输出，用户可能长时间看不到事件。Python Agent API 和 worker 放在内部网络，由 Java 执行对外身份与资源访问检查。

**OpenTelemetry Collector，按需独立部署。** 集中接收应用遥测，批处理、过滤并转发到相应观测后端；配合 SDK 关联 Java、Python、MQ 与工具调用。Collector 本身不是长期存储数据库；初期可以由 SDK 直接向兼容后端导出。它未被原方案规定为必须部署，故不计入上面的 9 类。

## 5. 按需求扩展：4 类

| 组件 | 项目用途 | 引入条件 |
|---|---|---|
| **Elasticsearch** | 文档词法检索、BM25、课程编号/名称/专业术语匹配；与 pgvector 的语义召回融合 | 固定评测证明词法召回是主要缺口后引入；初期可先做 PG 词法基线，但不能称其为 BM25 |
| **LiteLLM Proxy** | 统一多个模型提供方的接入、路由、故障切换与调用统计 | 当前百炼单提供方方案无需引入，先用小型 provider adapter；后续可先在百炼内做可选多模型实验，确有多提供方需求后再评估。业务审批/幂等仍由应用负责 |
| **vLLM** | 自部署模型推理服务，开展吞吐、首 Token 延迟、batch、KV cache 和显存实验 | 有硬件与研究需求时引入；使用托管模型 API 可先完成核心平台 |
| **Temporal** | 天级业务流程、定时器、补偿及跨服务持久工作流 | 现有持久化作业与 LangGraph 已不足以处理业务长流程时再评估，并明确两者编排边界 |

## 6. 不混入中间件数量的技术

| 技术 | 分类与用途 |
|---|---|
| 阿里云百炼模型 API | 托管模型服务；`qwen3.7-flash` 承担日常 Agent，`text-embedding-v4`（1024 维）承担 Embedding，两者共用一把百炼模型 API Key |
| Spring Boot、FastAPI、LangGraph | 应用框架 / Agent 编排库，运行在自己开发的服务中 |
| MyBatis-Plus、Flyway、Pydantic | ORM、数据库迁移、数据校验库/工具 |
| Docling、Ragas | 文档解析与评测工具库；worker 使用它们，不代表必须单独部署一套第三方平台 |
| MCP、A2A、SSE | 工具/Agent 通信与事件传输协议，不是独立服务产品 |
| OpenTelemetry SDK | 应用遥测库；与可独立部署的 Collector 分开统计 |
| Docker、Compose、Kubernetes、Helm | 容器与部署管理基础设施 |
| gVisor | 可选沙箱运行时，用于隔离不可信代码执行 |
| Testcontainers、Vitest、Playwright、k6、CI | 测试、压测和持续集成工具 |

这些技术仍有学习和维护成本，只是不计入上面“独立中间件/服务组件”的数量。

DeepSeek、硅基流动、智谱不再属于目标默认运行依赖。本地 BGE reranker 仅保留为可选对照实验，不增加厂商 Key；未验证收益前默认关闭重排并保留融合检索结果。现有代码读取系统环境变量 `API-KEY`，目标规范名 `DASHSCOPE_API_KEY` 在实现阶段再迁移，当前未更名。模型共用一把 Key 不涉及 OSS AccessKey、数据库密码等基础设施凭据的合并或删除。

## 7. 按一条业务链理解它们

~~~text
用户 → 反向代理 → Java API
                    ├─ Redis：登录态、限流、缓存
                    ├─ MySQL：权限、业务、审批、请求 + outbox
                    └─ RabbitMQ：可靠投递 / 唤醒
                           ↓
                    Python Agent Worker
                    ├─ PostgreSQL：运行、消息、事件、checkpoint
                    ├─ pgvector：语义检索
                    ├─ 百炼 API：qwen3.7-flash + text-embedding-v4，共用一把模型 Key
                    ├─ OSS：文档原文与大文件产物
                    ├─ Elasticsearch：可选词法召回
                    └─ Java Tool API → MySQL：审批后幂等预约

运行结果：PG 持久化事件 → Java 代理 SSE → 前端
效果分析：应用遥测 → Langfuse（自托管配 ClickHouse 等）
系统监控：应用/中间件指标 → Prometheus → Grafana
集中遥测：按需加入 OpenTelemetry Collector
~~~

建议按核心数据、可靠投递、评测观测、按需扩展的顺序实现。每新增一个组件，都应有对应的功能、故障测试或对照实验来证明其价值。
