# 知课行后端与 Agent 本机实验报告

实验日期：2026 年 10 月 1 日（北京时间）  
实验顺序：课程缓存 → 试听秒杀 → Agent 故障恢复 → Agent 任务与 RAG 评测  
项目：`zhikexing-backend`、`zhikexing-agent-runtime`；`zhikexing-web` 为关联前端，本轮未开展浏览器性能测试。

## 1. 实验目的与主要结果

本次实验衡量课程热读、异步成单和 Agent 业务执行的性能与正确性，为后端研发、Agent 研发岗位提供可复现的项目证据。负载和课程政策均为合成数据，实验运行于本机隔离服务；性能数值对应已测场景，不代表生产极限容量。

| 实验问题 | 本轮结果 | 主要判断 |
| --- | --- | --- |
| 两级缓存能否减少热读开销？ | 400 RPS 下，HTTP P95 三轮中位数由 3.935 ms 降至 2.446 ms；目录 SQL 调用减少 99.9917% | 热目录读场景的 SQL 与共享缓存访问均减少 |
| 异步秒杀链路的积压能否缓解？ | 80 个新增申请/s 下，窗口订单 TPS 由 25.50 增至 79.95；请求到订单时间戳差 P95 由 63.117 s 降至 230 ms | 缩短补发周期后，已测负载下的成单与排空速度提高 |
| Agent 重启与重放会否重复写业务？ | 4 类场景各 20 例，正式 80/80 通过；零重复动作、零未批准副作用 | 单 worker、确定性模型下的恢复与幂等检查通过 |
| 真实模型能否完成规定的工具合同？ | 5 条开发样本通过 4 条；30 条保留样本通过 21 条，规则通过率 70% | 业务安全检查与任务完成度需分开报告 |
| RRF 是否提高证据召回？ | 30 题合成保留集中，向量、词项、RRF 的 Recall@5 均为 100% | 本数据集已饱和，未观察到融合质量增益 |

## 3. 缓存：热读 SQL 减少，双实例冷键每轮只回源一次

### 3.1 对照方法

同一 JAR、鉴权、请求内容和资源配额下，比较直接查询 MySQL、Redis 单级缓存、Caffeine＋Redis 两级缓存。负载为 50% 默认课程首页、50% 固定课程详情，使用 5,000 个有效用户令牌轮换；令牌数量不等于同时在线或并发用户数量。

每档启动时以 100、300 RPS 各升温 10 秒；每轮预热 30 秒、测量 180 秒，共 3 轮，正式负载均为 400 RPS。客户端最大在途请求 128、空闲连接上限 32。两级缓存 L1 TTL 为 10 秒，L2 TTL 为 60 秒，L1 最大条目数为 1,000。

![400 RPS 下三档课程缓存对照](E:/dev/zhikexing-backend/experiments/evidence/figures/cache-evidence.png)

**图 1.** 左图为 HTTP P95 的三轮中位数，误差线为三轮最小–最大值；右图为测量窗口累计目录 SQL 调用 / 测量秒数。三档各测量 540 秒、216,000 次请求。数据由 [缓存发生器](E:/dev/zhikexing-backend/experiments/cache/run_cache.py) 采集，并由 [汇总脚本](E:/dev/zhikexing-backend/experiments/summarize.py) 和 [绘图脚本](E:/dev/zhikexing-backend/experiments/plot_evidence.py) 处理。

| 模式 | HTTP P95 中位数 [范围] / ms | 目录 SQL 总数 | 目录 SQL / s | 共享缓存查找总数 |
| --- | ---: | ---: | ---: | ---: |
| MySQL 直查 | 3.935 [3.850–4.361] | 324,000 | 600.00 | 0 |
| Redis | 2.786 [2.659–2.876] | 27 | 0.05 | 216,000 |
| Caffeine＋Redis | 2.446 [2.420–2.492] | 27 | 0.05 | 108 |

三档正式测量共 648,000 次请求，全部通过响应校验，无 HTTP 错误或发生器掉发。两级缓存相对直查的 P95 降低 37.84%，目录 SQL 调用降低 99.9917%；相对 Redis 单级缓存，目录共享缓存查找减少 99.95%。本地缓存记录 215,892 次命中、108 次未命中，命中率为 99.95%。

Redis 和两级缓存的 SQL 调用相同，表明本场景中增加 L1 的主要收益是减少共享缓存访问；SQL 减少主要来自共享缓存复用。该结果针对两个固定热路径，尚未衡量长尾查询、缓存污染或大范围筛选条件。

### 3.2 双实例冷缓存

每轮等待 10.5 秒使 L1 过期，再删除一个明确的实验 L2 value key，同时释放请求至两个实例。100、300 个并发请求各测 10 轮，共 20 轮、4,000 次请求；所有响应通过校验，每轮两实例合计 loader 调用和详情 SQL 调用均为 1。结果支持本次单热键场景下的跨实例回源协调，不代表多热点或最大并发容量。

## 4. 试听秒杀：缩短补发周期后，80/s 负载下积压减少

### 4.1 工作负载与单变量对照

请求经过真实 HTTP 受理、MySQL 持久申请、RocketMQ 事务消息、Redis Lua 库存预留及 MySQL 订单路径。两组使用相同 JAR，补发选择批量均为 30，仅将每轮完成后的 fixed delay 从 1,000 ms 改为 100 ms；未改变发送并发或消费者线程配置。

每组包含 5 类场景，各重复 3 次，共 15 个阶段：100 个名额、1,000 个申请在约 10 秒内以 100/s 到达的售罄场景，以及库存 10,000、持续 30 秒的 5、20、40、80 个新增申请/s 场景。每阶段另有 20% 相同幂等键的 HTTP 重放，各阶段使用新活动。1,000 个申请并非 1,000 个同时在途请求。

![80 个新增申请每秒下的成单时延与窗口吞吐](E:/dev/zhikexing-backend/experiments/evidence/figures/trial-evidence.png)

**图 2.** 80 个新增申请/s＋20% HTTP 重放，30 秒提交、三次重复，补发批量为 30。左图为请求到订单数据库时间戳差 P95；右图为 `[5,25)` 秒窗口订单 TPS。柱高是三轮中位数，误差线是最小–最大范围；HTTP 202 仅表示受理。

| 新增申请速率 / s | 基线成单 P95 / ms | 优化成单 P95 / ms | 基线窗口 TPS | 优化窗口 TPS |
| --- | ---: | ---: | ---: | ---: |
| 5 | 1,032 | 122 | 5.10 | 5.00 |
| 20 | 1,138 | 129 | 19.80 | 20.05 |
| 40 | 18,444 | 148 | 24.00 | 40.10 |
| 80 | 63,117 | 230 | 25.50 | 79.95 |

80/s 档的订单 TPS 增至基线的 3.14 倍，成单 P95 降低 99.64%；基线 P95 三轮范围为 62.845–63.640 秒，优化为 226–231 ms。最后一笔申请后的数据库积压排空时间中位数由 66.306 秒降至 0.192 秒。同期 HTTP 受理 P95 为 54.156→54.697 ms，变化主要出现在后续异步成单环节。

基线发送器每轮顺序发送后再等待 1 秒，实际吞吐不能按“30 条/秒”直接推定。高于约 25 TPS 的已测到达速率下，基线出现积压；缩短等待后，40/s 和 80/s 档窗口成单速率接近到达速率。80/s 为本次测量上限，未测系统极限。

### 4.2 库存与幂等校验

两组 30 个阶段合计 32,100 笔首次申请、6,420 次重放，即 38,520 次 POST；实际产生 26,700 笔订单，另有 5,400 笔售罄拒绝。两组各产生 13,350 笔订单；HTTP 及数据库断言全部通过，未观察到超卖、重复申请键、重复订单或成功申请缺订单。

客户端终态轮询总速率最高 50 GET/s，可能引入观察延迟，因此报告优先使用数据库时间戳差。对账依据为申请与订单联表导出及库存检查，未据此额外宣称扫描了数据库内全部孤儿订单。

## 5. Agent 恢复：60 次进程故障和 20 组重放均通过

### 5.1 故障窗口与验证方法

恢复实验采用 fixture 确定性模型，使用真实 PostgreSQL 状态、Java 工具接口、MySQL 审批与预约记录。测试器只停止自己创建的 Runtime 子进程，Java、MQ 和数据库保持运行。单 Uvicorn worker 下，对四类场景各测 20 次。

| 场景 | 故障或扰动 | 核心断言 |
| --- | --- | --- |
| 持久入队后停止 | 将任务持久为 QUEUED，再停止、启动 Runtime | 同一 run 恢复，单输入、单答案、单完成事件 |
| 等待审批时停止 | 持久化草稿并确认零预约，Runtime 停止期间在 Java 批准，再启动 | 同一审批与 action 恢复，只产生一笔预约 |
| 提交成功后丢响应 | 代理确认真实 Java 执行成功后扣留响应，停止 Runtime，再启动 | 崩溃前已提交，恢复后仍为同一预约，不重复执行副作用 |
| 重复命令与执行请求 | 每例重放 Java 受理 10 次、Python HTTP 投递 10 次、已批准执行 5 次 | 收敛到同一 run 和预约回执，无额外业务记录 |

![Agent 四类恢复与重放实验](E:/dev/zhikexing-backend/experiments/evidence/figures/agent-recovery-evidence.png)

**图 3.** 四类场景各 20 例，全部通过 PG 状态、事件唯一性与 MySQL 副作用检查。模型为 fixture；第三类确实扣留真实提交后的成功响应，第四类为 HTTP 边界重放，并非强制 RocketMQ broker 重投。

| 场景 | 通过数 | 健康就绪→终态 P95 / ms | 进程启动→健康 P95 / ms |
| --- | ---: | ---: | ---: |
| 持久入队后停止 | 20/20 | 166.626 | 2,548.442 |
| 等待审批时重启 | 20/20 | 335.597 | 3,214.533 |
| 提交成功后丢响应、重启 | 20/20 | 322.921 | 3,380.247 |
| 重复命令与执行请求 | 20/20 | 933.929（批准响应收到→终态） | 不适用 |

正式实验共 80/80 通过，包含 60 个进程故障样本和 20 组共 500 次附加重放，实际产生 60 条业务副作用；重复动作、未批准写入均为零。提交后丢响应的 20 个样本另做故障窗口核验：崩溃前恰有一笔预约、代理回执与该预约一致，恢复后仍为同一预约。

前三类按每例“启动至健康＋健康至终态”相加后再计算 P95，分别为 2.710、3.383、3.553 秒；不是把两列 P95 相加。该时钟仍排除故障发现、停止进程和启动前操作，不称为完整故障恢复 RTO。80 个有限样本的通过率也不等于生产可用性。

## 6. 真实 Agent：业务写入对账通过，严格任务合同仍有失败

### 6.1 冻结数据集与评分

任务集共 50 条，覆盖课程查询、校区查询、缺信息、预约批准/拒绝、试听查询/批准/拒绝、未开场试听、RAG 共 10 类。划分为开发集 20 条、保留集 30 条；本轮实际执行 5 条开发集代表样本及全部 30 条保留样本，剩余 15 条开发样本未执行。

使用 qwen3.7-flash 运行完整 Agent 图，经真实 Java 受理与工具、审批及 MySQL 对账。每例创建独立工作空间；审批决定由测试器自动提交，试听场景使用独立活动。评分器版本为 `agent-contract-v2-business-fields`，校验工具策略、目标状态、审批、实际副作用、显式姓名/联系方式与批准参数一致性，以及部分事实和引用断言。数据集、策略及评分器在两批真实评测之间保持不变。

| 分组 | 实际执行 | 规则通过 | 规则通过率 | 图执行耗时 P95 / s | 已知 chat 估算 / 元 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 开发样本 | 5 | 4 | 80% | 6.806 | 0.0078614 |
| 保留样本 | 30 | 21 | 70% | 16.483 | 0.0355756 |

任务顺序执行，不能据此声称 Agent 高并发容量。图执行耗时包括自动审批往返，排除语料准备，且不包含部分试听后续数据库终态等待；也不是统一的成功业务办理时延。规则分不评估全部自然语言语义，`semanticCorrectness` 保持未评分。

### 6.2 业务安全与失败分析

35 条任务均保存 MySQL 只读快照；7 个进入审批的样本在采集到的审批前观测点均为零副作用。实际产生 1 笔预约、3 笔试听订单，4 组 Java 回执与数据库一致；未批准写入、重复 action 和缺失预约行均为零。唯一落库预约的姓名、电话、课程与校区匹配输入及批准参数，此项参数正确性核验的分母仅为 1 笔预约。审批前快照是离散观测，不是连续监控。

保留集 9 个失败按原规则保留，AI 辅助诊断如下；诊断不回溯改分，也不代替人工语义评价。

| AI 辅助归因 | 数量 | 解释 |
| --- | ---: | --- |
| 澄清课程/校区与严格草稿合同不匹配 | 5 | 模型先追问选择，未生成评分器要求的草稿；需要区分安全澄清与目标完成 |
| 忽略已提供的姓名 | 1 | 已有输入未被正确利用 |
| 委托选择与再次澄清的意图歧义 | 1 | 模型对是否代选的理解与任务合同不同 |
| 长回答未完成必要信息询问 | 1 | 姓名、联系方式等要求未完整落实 |
| 省略规定查询工具 | 1 | 直接生成试听草稿，批准后真实成单，但工具路径不满足合同 |

开发集另有 1 个预约任务因先澄清课程/校区而未生成草稿，记为失败。规则通过的部分回答仍出现学历编码解释错误、返回 50 条却声称 48 条、输出不完整，以及建议重新批准已拒绝草稿等问题。两条保留集 RAG 回答中的“21 天”“24 小时”有对应引用支持，这只是逐例 AI 辅助观察。

## 7. RAG：三种检索均达到合成集上限，融合增益未体现

冻结 25 个合成课程的 100 个政策 chunk 和 50 道问题，使用 text-embedding-v4 的 1024 维真实向量。开发 20 题、保留 30 题使用不同课程身份，但问句模板重复；保留集包含 22 道单证据题和 8 道双证据题。

比较 pgvector 精确余弦排序、中文词项重叠和固定 RRF(k=60)，没有使用 ANN、BM25 或 reranker。向量先生成并固定缓存，对照阶段无模型调用。每题每种方法测量 5 次，变体顺序按固定种子打乱，共保留 150 条题目/方法记录、750 条计时样本。

![真实冻结向量下的 RAG 保留集召回率](E:/dev/zhikexing-backend/experiments/evidence/figures/rag-evidence.png)

**图 4.** 100 个合成 chunk、30 道保留问题，三种方法的 macro Recall@5 均为 100%。课程身份划分独立，但题型模板重复，本图不衡量生成答案的准确率。

| 保留集方法 | Recall@5 | MRR@5 | 完整证据覆盖率 | 检索 P95 / ms |
| --- | ---: | ---: | ---: | ---: |
| 向量 | 100% | 1.00 | 100% | 1.778 |
| 词项重叠 | 100% | 1.00 | 100% | 1.617 |
| RRF | 100% | 1.00 | 100% | 3.503 |

本数据集未区分三种方法的检索质量；RRF 的检索 P95 更高，不能写成融合提高召回或降低时延。该结果支持对照管线与标签覆盖检查已建立，但不足以判断实际课程知识库的检索收益。

检索计时包括数据库查询与必要的 Python 排序，排除 embedding、生成、HTTP 和鉴权。保留问题的独立 query embedding P95 为 184.563 ms，来自准备阶段每题一次的调用记录；不能与检索 P95 相加当作端到端 P95。向量准备记录 5,848 embedding tokens，embedding 费用未归集。

## 9. 后续实验与简历取舍

| 已发现的问题 | 下一步可检验实验 | 主要观察量 |
| --- | --- | --- |
| 学历枚举解释错误、长回答遗漏或截断 | 在开发集显式提供字段映射、限制列表长度、记录生成结束原因 | 字段解释错误率、完整回答率、显式输入遗漏率 |
| 草稿与澄清合同存在意图歧义 | 新版本任务集分别标注允许代选、必须追问、必须草稿；用新的未见保留集评测 | 目标完成率、安全澄清率、未批准副作用；当前保留集保留为回归集 |
| RAG 小型合成集饱和 | 加入同名课程、别名改写、冲突版本、无答案题和难负例，隔离问句模板 | Recall@5、MRR@5、完整证据覆盖、无答案误答率 |
| 恢复尚未覆盖真实模型故障 | 另测超时、429、部分流式输出及恢复后的重复模型调用 | 业务副作用唯一性、恢复时延、重复 token 与费用 |
| 本轮未测最大容量 | 单独扩展有效负载发生器和更大数据规模，以错误率、尾时延、资源饱和共同确定容量拐点 | 成功吞吐、P99、掉发、积压与资源占用 |

现阶段简历优先使用有对照或故障窗口证据的三项结果；Agent 第二项可突出评测体系建设，而不把尚未充分评价的质量分写成准确率。

- **后端缓存：** 基于 Caffeine、Redis 和 Redisson 实现课程目录两级缓存与并发回源协调；本机 400 RPS、三档各 3×180 秒热读对照中，HTTP P95 三轮中位数由 3.94 ms 降至 2.45 ms，目录 SQL 调用减少 99.99%；双实例 100/300 并发冷键请求共 20 轮均只触发一次回源。
- **后端异步成单：** 基于 Redis Lua、RocketMQ 事务消息与 MySQL 幂等约束实现试听抢购，将补发间隔由 1 秒调整为 100 ms；80 个新增申请/s＋20%重放下，窗口订单 TPS 由 25.50 增至 79.95，请求到订单时间戳差 P95 由 63.12 秒降至 230 ms；30 个阶段共生成 26,700 笔订单，未观察到超卖或重复订单。
- **Agent 恢复与幂等：** 基于持久状态与业务幂等回执验证任务恢复；确定性模型、真实 Java/数据库环境下，完成持久入队、审批等待、提交后响应丢失及命令重放四类 80 例检查，全部通过；500 次附加重放未产生重复或未批准业务副作用。
- **Agent 评测体系：** 建立覆盖 10 类场景的 50 条冻结任务集，完成 35 条真实模型全链路任务和 Java/MySQL 对账，定位澄清策略、显式字段遗漏及枚举解释问题；另建立 100 块语料、50 道标注问题的检索对照与证据覆盖评测，保留 750 条计时记录。

70% 为本轮保留集规则通过率，尚不宜作为质量优化成果；RAG 三种策略均达该合成集上限，也不支持“融合提升召回”的简历表述。
